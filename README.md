# PII-фильтр: очистка персональных данных перед отправкой во внешние LLM

Бэкенд-сервис (без фронта, по ТЗ): один эндпоинт принимает текст или файл (PDF/DOCX/TXT)
и возвращает текст, очищенный от персональных данных. Ставится сбоку от корпоративного
гейтвея: гейтвей шлёт сюда содержимое запроса, получает очищенную версию и отправляет её
во внешнюю LLM — сами ПДн контур компании не покидают.

## Архитектура очистки: три слоя

1. **Регексы** — однозначные машинные форматы: телефоны (в т.ч. слитно `89261234567`),
   email, СНИЛС, ИНН, расчётные счета, карты, паспорта. Миллисекунды, ноль ложных срабатываний.
2. **NER (Natasha)** — русские ФИО (включая инициалы и падежи), организации, адреса.
   Локальная лёгкая модель, заточенная под русский язык. + эвристики на «филиал/обособленное
   подразделение» (по ТЗ филиалы — тоже ПДн) и организации в кавычках.
3. **Контекстный LLM-слой** (Ollama, маленькая модель) — только для случаев, где нужен контекст:
   - **даты**: дата рождения — вычищается, дата подписания/срок исполнения — остаётся.
     Сначала эвристика по ближайшему ключевому слову, спорные даты — в LLM;
   - **аудит вторым проходом**: модель проверяет уже очищенный текст и находит пропуски
     первых слоёв (типично — названия компаний без ООО и кавычек).

Экономика: LLM видит только спорные фрагменты и короткий очищенный текст, а не каждый документ —
основную массу закрывают слои 1–2 за ~4 мс. Сомнение всегда трактуется в сторону вычищения
(ложное срабатывание лучше утечки).

Найденное заменяется плейсхолдерами `[ФИО_1]`, `[ТЕЛЕФОН_1]`...— текст остаётся читаемым
для внешней LLM, связи между повторными упоминаниями сохраняются (одно значение — один плейсхолдер).

## Структура

```
pii-filter/
├── app/
│   ├── pii.py        # слои 1–2: регексы + Natasha + слияние + плейсхолдеры
│   ├── llm.py        # слой 3: классификация дат + аудит остатка (Ollama)
│   ├── main.py       # FastAPI: /clean (текст), /clean/file (PDF/DOCX/TXT), /health
│   ├── corpus.py     # генератор размеченного корпуса (120 док., 600+ PII, 300 ловушек)
│   └── evaluate.py   # метрики: recall, keep-rate, latency; python -m app.evaluate [--llm]
├── data/corpus.json  # корпус с эталонной разметкой
├── Dockerfile, docker-compose.yml, .env.example, requirements.txt
```

## Запуск

```powershell
Copy-Item .env.example .env   # проверь LLM_MODEL (из `ollama list`)
docker compose up --build -d
```

Swagger: http://localhost:8002/docs

```bash
# текст
curl -X POST "localhost:8002/clean" -H "Content-Type: application/json" \
  -d '{"text": "Свяжитесь с Ивановым И.И. по тел. 89261234567 до 20.08.2026"}'
# файл
curl -X POST "localhost:8002/clean/file" -F "file=@dogovor.pdf"
```

Режимы: `?mode=fast` — без LLM (~4 мс), `?mode=full` — с контекстным слоем (по умолчанию).
Без Ollama: `MOCK_MODE=true` — работает fast-слой.

## Метрики (методология)

Корпус — 120 синтетических русских документов (договоры, акты, заявки, уведомления) с
эталонной разметкой: 600+ PII-сущностей 14 типов и ~300 «ловушек» — значений, которые фильтр
трогать НЕ должен (даты подписания, сроки, суммы, номера договоров, ссылки на законы).
В корпус специально включены трудные случаи: инициалы, телефоны слитно, даты рождения
прописью, организации без правовой формы и кавычек.

- **recall** — доля вычищенных PII (главная метрика: «чтобы не пропускал»); утечкой считается
  в т.ч. уцелевшая фамилия из ФИО или цифровая форма номера;
- **keep-rate** — доля уцелевших ловушек (прокси precision: не калечим полезный текст);
- **latency** — mean/median/p95 на документ; для LLM-режима также токены.

Запуск: `python -m app.evaluate` (слои 1–2) и `python -m app.evaluate --llm` (полный пайплайн).
Отчёты пишутся в `data/eval_*.json`.

Фактические цифры: см. раздел «Результаты» ниже (заполняется после прогонов, включая
сравнение моделей qwen2.5:1.5b vs gemma3:4b и тест на реальных документах с zakupki.gov.ru).

## Статус

Реализовано и проверено: пайплайн очистки (regex + NER + контекстный слой), API (/clean, /clean/file),
генератор размеченного корпуса, оценка метрик. Базовые цифры (без LLM-слоя): recall 99.5%,
keep-rate 100%, ~4 мс/документ.
В работе: прогон полного пайплайна с LLM, сравнение qwen2.5:1.5b vs gemma3:4b,
тест на реальных документах zakupki.gov.ru — результаты будут добавлены в этот раздел.

## Результаты (финальные)

Сравнение конфигураций на размеченном корпусе (120 док., 611 PII, 296 ловушек):

| Конфигурация | Recall | Keep-rate | Latency |
|---|---|---|---|
| regex + NER | 99.5% | 100% | ~6 мс/док |
| + аудит qwen2.5:1.5b | 99.5% (аудит бесполезен) | 100% | ~1.1 с/док |
| + аудит gemma3:4b | **100%** | 92.9% | ~12 с/док |

Вывод: 1.5b не тянет аудит русского текста; gemma3:4b добирает пропуски NER до полного recall ценой
латентности. Рекомендация: regex+NER на потоке, LLM-аудит асинхронно для чувствительных документов.

## Тест на реальных документах (zakupki.gov.ru)

Реальный контракт (87 тыс. символов, DOCX): все PII вычищены без утечек (ФИО в падежах, телефоны,
email, ИНН, счета, адреса, организация в 5 написаниях), 75 сущностей за 26 с (2 LLM-вызова, ~2.3 тыс.
токенов). Реальные документы вскрыли 7 классов ложных срабатываний, не проявившихся на синтетике
(коды ОКПД2 как даты, договорные термины как ФИО, даты законов как даты рождения, телефоны из середины
кодов закупок, каскадная чистка плейсхолдеров LLM-аудитором и др.) — все закрыты валидацией
(проверка календарной корректности дат, границы цифр, стоп-листы терминов/стран/валюты).
Известное ограничение: NER изредка захватывает договорный термин с соседним словом
(«Заказчик прилагает» -> [ОРГАНИЗАЦИЯ]) — не ломает текст, ~6 случаев на 87 тыс. символов.

## Полный цикл гейтвея: /clean -> внешняя LLM -> /restore

Односторонняя очистка решает половину задачи: обезличенный текст уходит наружу, но
пользователю нужен ответ с настоящими именами. Поэтому `/clean` возвращает карту
подстановок (`removed`), а эндпоинт `/restore` принимает ответ внешней модели вместе
с этой картой и подставляет исходные значения обратно.

```
POST /clean    {"text": "Клиент Смирнов Пётр Николаевич, тел. 89261234567"}
  -> cleaned_text: "Клиент [ФИО_1], тел. [ТЕЛЕФОН_1]"
     removed: [{"type":"fio","value":"Смирнов Пётр Николаевич","placeholder":"[ФИО_1]"}, ...]

  (наружу во внешнюю LLM уходит только cleaned_text)

POST /restore  {"text": "Свяжитесь с [ФИО_1] по номеру [ТЕЛЕФОН_1]", "removed": [...]}
  -> restored_text: "Свяжитесь с Смирнов Пётр Николаевич по номеру 89261234567"
```

Карта подстановок остаётся на стороне гейтвея и наружу не передаётся. Плейсхолдеры,
которых нет в карте, не подставляются и возвращаются в поле `unknown_placeholders` —
это признак того, что модель их выдумала.

## Задержка по слоям

Цена каждого слоя измерена отдельно (`python -m app.bench_latency`, 120 документов,
медиана / p95 / максимум — среднее по такой выборке малоинформативно): результаты в
`results/latency.md`. Регексы работают за десятые доли миллисекунды, NER-слой дороже
их на порядок с лишним, но в абсолютных величинах остаётся единицами миллисекунд —
то есть на потоке гейтвея незаметен. Реальная граница проходит по LLM-аудиту:
он переводит задержку из миллисекунд в секунды, поэтому применять его имеет смысл
не на всём трафике, а выборочно — для чувствительных документов.

## Холодный старт LLM-слоя

После простоя Ollama держит модель выгруженной, и первая загрузка `gemma3:4b` занимает
около 20 секунд. В это время сервер отвечает на запросы не ожиданием, а 500 — то есть
первый же реальный запрос к фильтру падал на ровном месте (поймано при прогоне бенчмарка).

Закрыто с двух сторон: при старте сервиса модель прогревается заранее (результат виден
в `/health` как `model_warm`), а запросы к Ollama повторяются до трёх раз с паузой, если
ответ 5xx или обрыв соединения. Клиентские ошибки (404 «нет такой модели») не
повторяются — это не временный сбой. Если Ollama не поднята, сервис всё равно
стартует: LLM-слой просто не используется.
