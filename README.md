# PII-фильтр: очистка персональных данных перед отправкой во внешние LLM

Бэкенд-сервис (без фронта, по ТЗ): один эндпоинт принимает текст или файл (PDF/DOCX/TXT)
и возвращает текст, очищенный от персональных данных. Ставится сбоку от корпоративного
гейтвея: гейтвей шлёт сюда содержимое запроса, получает очищенную версию и отправляет её
во внешнюю LLM — сами ПДн контур компании не покидают.

## Архитектура очистки: три слоя

1. **Регексы** — однозначные машинные форматы: телефоны (в т.ч. слитно `89261234567`),
   email, СНИЛС, ИНН, расчётные счета, карты, паспорта. Миллисекунды, ноль ложных срабатываний.
2. **NER (Natasha)** — русские ФИО (включая инициалы и падежи), организации, адреса.
   Локальная лёгкая модель, заточенная под русский язык. + эвристики на «филиал/обособленное
   подразделение» (по ТЗ филиалы — тоже ПДн) и организации в кавычках.
3. **Контекстный LLM-слой** (Ollama, маленькая модель) — только для случаев, где нужен контекст:
   - **даты**: дата рождения — вычищается, дата подписания/срок исполнения — остаётся.
     Сначала эвристика по ближайшему ключевому слову, спорные даты — в LLM;
   - **аудит вторым проходом**: модель проверяет уже очищенный текст и находит пропуски
     первых слоёв (типично — названия компаний без ООО и кавычек).

Экономика: LLM видит только спорные фрагменты и короткий очищенный текст, а не каждый документ —
основную массу закрывают слои 1–2 за ~4 мс. Сомнение всегда трактуется в сторону вычищения
(ложное срабатывание лучше утечки).

Найденное заменяется плейсхолдерами `[ФИО_1]`, `[ТЕЛЕФОН_1]`...— текст остаётся читаемым
для внешней LLM, связи между повторными упоминаниями сохраняются (одно значение — один плейсхолдер).

## Структура

```
pii-filter/
├── app/
│   ├── pii.py        # слои 1–2: регексы + Natasha + слияние + плейсхолдеры
│   ├── llm.py        # слой 3: классификация дат + аудит остатка (Ollama)
│   ├── main.py       # FastAPI: /clean (текст), /clean/file (PDF/DOCX/TXT), /health
│   ├── corpus.py     # генератор размеченного корпуса (120 док., 600+ PII, 300 ловушек)
│   └── evaluate.py   # метрики: recall, keep-rate, latency; python -m app.evaluate [--llm]
├── data/corpus.json  # корпус с эталонной разметкой
├── Dockerfile, docker-compose.yml, .env.example, requirements.txt
```

## Запуск

```powershell
Copy-Item .env.example .env   # проверь LLM_MODEL (из `ollama list`)
docker compose up --build -d
```

Swagger: http://localhost:8002/docs

```bash
# текст
curl -X POST "localhost:8002/clean" -H "Content-Type: application/json" \
  -d '{"text": "Свяжитесь с Ивановым И.И. по тел. 89261234567 до 20.08.2026"}'
# файл
curl -X POST "localhost:8002/clean/file" -F "file=@dogovor.pdf"
```

Режимы: `?mode=fast` — без LLM (~4 мс), `?mode=full` — с контекстным слоем (по умолчанию).
Без Ollama: `MOCK_MODE=true` — работает fast-слой.

## Метрики (методология)

Корпус — 120 синтетических русских документов (договоры, акты, заявки, уведомления) с
эталонной разметкой: 600+ PII-сущностей 14 типов и ~300 «ловушек» — значений, которые фильтр
трогать НЕ должен (даты подписания, сроки, суммы, номера договоров, ссылки на законы).
В корпус специально включены трудные случаи: инициалы, телефоны слитно, даты рождения
прописью, организации без правовой формы и кавычек.

- **recall** — доля вычищенных PII (главная метрика: «чтобы не пропускал»); утечкой считается
  в т.ч. уцелевшая фамилия из ФИО или цифровая форма номера;
- **keep-rate** — доля уцелевших ловушек (прокси precision: не калечим полезный текст);
- **latency** — mean/median/p95 на документ; для LLM-режима также токены.

Запуск: `python -m app.evaluate` (слои 1–2) и `python -m app.evaluate --llm` (полный пайплайн).
Отчёты пишутся в `data/eval_*.json`.

Фактические цифры: см. раздел «Результаты» ниже (заполняется после прогонов, включая
сравнение моделей qwen2.5:1.5b vs gemma3:4b и тест на реальных документах с zakupki.gov.ru).

## Статус

Реализовано и проверено: пайплайн очистки (regex + NER + контекстный слой), API (/clean, /clean/file),
генератор размеченного корпуса, оценка метрик. Базовые цифры (без LLM-слоя): recall 99.5%,
keep-rate 100%, ~4 мс/документ.
